# Prompt 003 — PostgreSQL Integration Validation & Phase 2 Hardening

Repository: https://github.com/DesKaOne/DesKaOne-Control-Center  
Target branch: `feat/phase2-postgresql-security`  
Baseline expected: `91cb0bb8a9390ca36c31a31a9de0065ed1cfd060` or a later commit.

## Misi
Validasi implementasi Prompt 001–002 menggunakan PostgreSQL 17 sungguhan pada database TEST yang terisolasi; perbaiki hanya bug yang terbukti dan tingkatkan keamanan serta kualitas pengujian. Jangan menambah provider baru dulu. Semua UI dan dokumentasi pengguna dalam Bahasa Indonesia. Backend Go saja, tanpa Python, sesuai `AGENTS.md`.

## 0. Git safety / persiapan
- Baca `AGENTS.md`, `README.md`, `docs/SECURITY.md`, `docs/PHASE2-CHECKPOINT.md`, migrasi 000001/000002, konfigurasi PostgreSQL dan seluruh integration tests.
- Pastikan branch benar dan working tree bersih; fetch remote dan pastikan HEAD lokal tidak tertinggal. Prompt ini di-push sebagai commit baru ke branch yang sama: gunakan `git pull --ff-only` hanya bila working tree bersih dan tidak divergen.
- Jangan reset, rebase, force push, stash, clean, menimpa perubahan lokal, ataupun merge ke `main`.
- Jika branch divergen, worktree kotor, atau ada konflik, hentikan perubahan dan laporkan opsi aman.

## 1. Integration test nyata PostgreSQL 17 (prioritas utama)
- Verifikasi `docker info`, `docker compose config`, dan kondisi container tanpa menampilkan password atau menghapus volume.
- `DKO_TEST_DATABASE_URL` wajib menunjuk database test terpisah yang jelas, misalnya `deskaone_control_test`, BUKAN `deskaone_control`/produksi. Tolak URL yang tampak bukan test, host remote yang tidak disetujui, atau DB yang mengandung data pengguna; jangan berasumsi aman karena nama variabel.
- Bila Docker daemon/psql/DB tidak tersedia, jangan memalsukan PASS. Sebagai gantinya tambahkan panduan PowerShell lengkap dan aman untuk menjalankan setup manual. Jangan menginstal Docker/psql secara otomatis.
- Jangan menjalankan migrasi pada DB non-test. Untuk database test baru yang secara eksplisit dipastikan kosong dan disposable, buat database test secara aman hanya bila operator memberi izin; periksa daftar DB, skema, dan target koneksi terlebih dahulu.
- Jalankan migrasi `000001_phase2.up.sql` lalu `000002_provider_accounts_management.up.sql` secara eksplisit pada DB test tersebut, dengan `ON_ERROR_STOP=1`. Catat statusnya. Jangan ulang migrasi ke DB existing tanpa pengecekan schema state.
- Jalankan `go test -v -tags=integration ./internal/database -count=1`, catat PASS/FAIL/SKIP masing-masing. Bila perlu perluas integration tests untuk: akun terisolasi, multi-account same provider, concurrent idempotent collector runs, error rollback, penyimpanan credential encrypted, AAD UUID binding, disabled accounts, saldo terakhir tidak menjadi nol saat gagal, dan constraint DB.
- Jangan melakukan `docker compose down -v`, DROP/TRUNCATE terhadap DB/volume yang sudah ada, atau menghapus data untuk mengulang test.

## 2. Review migrations / database correctness
- Audit 000001 dan 000002 termasuk up/down ordering, uniqueness `(provider_slug, account_key)`, constraints, foreign keys, indeks, identitas provider account pada collector_run dan snapshot, serta retry idempotency.
- Jika perubahan skema sudah mungkin diterapkan, perbaiki via migrasi versioned baru (`000003`), jangan mengedit migrasi applied secara sembarangan. Down migration yang berisiko kehilangan data harus fail-safe.
- Validasi sqlc source queries versus checked-in generated code. Bila `sqlc` tersedia, jalankan `sqlc generate` dan periksa diff; bila tidak, laporkan belum diverifikasi generator.

## 3. Hardening credential / admin
- Review jalur UI `/admin/providers` end-to-end: auth sesi, CSRF pada seluruh POST, validasi input, body limit, multi-account, audit tanpa rahasia, error Bahasa Indonesia.
- Pastikan ciphertext AES-256-GCM, nonce, master key, password, cookies, JWT, API key, dan header Authorization tidak bocor ke HTML, JSON, error, atau log; uji bahwa AAD account ID mencegah swap ciphertext antar akun.
- Periksa fallback `.env` untuk akun `default`: hanya berlaku dalam keadaan kompatibilitas eksplisit dan tidak menimpa akun vault; dokumentasikan cara mematikannya setelah migrasi credential.
- Periksa handling token expired, error klasifikasi 401/403 vs 5xx/timeout vs malformed; jangan catat balance 0 palsu ketika gagal.
- Lakukan review SSRF/redirect, HTTPS cookie flag, login rate limiting, session invalidation dan security headers. Perbaiki bug terkonfirmasi disertai tests; risiko yang butuh desain lebih besar dicatat sebagai backlog, jangan tiba-tiba menambah fitur besar seperti MFA atau RBAC.

## 4. Verifikasi dan deliverables
- Jalankan `gofmt`, `go test ./...`, `go vet ./...`, `go test -race ./...`, `git diff --check` bila tools tersedia. Nyatakan PASS/SKIP/FAIL dengan benar.
- Tambahkan/update `docs/PHASE2-VALIDATION.md` dan `docs/PHASE2-CHECKPOINT.md` termasuk bukti hasil uji nyata, command Windows PowerShell aman, langkah migrasi test manual, limitation serta risiko residual.
- Jangan commit `.env`, token, log credential, database dump, fixture yang memuat secret asli, atau artefak pribadi.
- Jangan tambah GitHub Actions; jangan memodifikasi repo lain; jangan deploy VPS; jangan menjalankan migrasi produksi; jangan merge `main`.
- Setelah perubahan yang benar-benar selesai diuji, buat commit **lokal** pada branch fitur. **Jangan push kode/PR** sampai pengguna meminta.

## Format laporan Codex
1. Ringkasan masalah yang ditemukan/diperbaiki.
2. Migration 000001/000002: PASS/FAIL/NOT RUN beserta bukti dan alasan; jika ada 000003 jelaskan kenapa.
3. Integration test PostgreSQL: hasil aktual per test (bukan sekadar compile/skip).
4. Unit test, vet, race, diff-check: status nyata.
5. Temuan security yang tersisa, tingkat risiko, dan alasan tidak dibenahi sekarang.
6. File yang berubah, commit SHA lokal, status working tree.
7. Langkah PowerShell untuk menguji ulang di Windows (tanpa mencetak secret).
8. Apakah Phase 2 siap code review, serta blocker produksi yang tersisa.

Selesaikan semaksimal mungkin dalam satu sesi tanpa mengubah data yang tidak dapat dipastikan aman. Bila DB test tidak tersedia, hasil yang benar adalah SKIP + panduan pengujian, bukan klaim selesai produksi.
